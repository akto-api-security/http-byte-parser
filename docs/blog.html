Turning a raw []byte into an HTTP request, as fast as the machine allows

A traffic pipeline was pinning every CPU at ~30k request/response pairs per second. The culprit wasn't the network — it was http.ReadRequest allocating its way into the garbage collector. This is the story of parsing HTTP by slicing instead of copying, across seven implementations in two languages.

The problem

Why the stock parser is the bottleneck

Go's http.ReadRequest is general and correct — it streams from a bufio.Reader, builds a map[string][]string of headers, parses a url.URL, and hands you a live body reader. For a server that's exactly right. For a pipeline that already holds the complete message in one []byte and just needs the fields out, it's ~16 allocations and ~1.25 KB of garbage per message.

At 30k pairs/sec that allocation firehose kept the garbage collector running on every core — a CPU profile of the production pipeline showed over half the time in mallocgc and GC, with parsing and json.Marshal as the two ~21% giants. The parse was never slow because the algorithm was slow; it was slow because it allocated.

The whole idea

The bytes are already in memory. Don't copy them into strings and maps — record where each field starts and ends, and decode lazily only what you read. A parsed field becomes a slice pointing back into the original buffer.

Techniques

What actually moved the needle

CORE

Zero-copy slices

A field is a window into the buffer — buf[i:j], a pointer and a length. No sub-strings, no header map. The single biggest win: from ~16 allocations to zero.

SCAN

SIMD delimiter search

Finding \r\n and : is the hot loop. bytes.IndexByte (Go) and memchr (C) are hand-tuned vector assembly — 16–32 bytes per instruction. 2.2× over a scalar loop.

LAYOUT

Packed offsets

Store header positions as four uint32s, not two 24-byte slice headers. ~4× less memory written per header keeps the cache hot and the allocator idle.

ENCODE

Hand-rolled JSON

The output stage mattered as much as the parse. Skipping json.Marshal + the header maps and appending bytes straight into a pooled buffer cut the encoder from 44 allocations to 0.

TRADE

Validation is not free

cfast's 3× lead was mostly the cost of safety it skipped. A real traffic parser must reject malformed input, not crash on it — so we escape invalid UTF-8 and return errors, and accept the slower number.

BRIDGE

The cgo tax

Calling the fast C parser from Go cost ~40–250 ns at the boundary — larger than the 20 ns parse itself. Per-message cgo erased the win entirely; only batching thousands per call helps.

Go vs C

Which language wins?

The surprising answer on Apple Silicon: well-written Go matched or beat stock C. Go's bytes.IndexByte carries SIMD for both amd64 and arm64 and picks the right one at runtime — while picohttpparser's SIMD is #ifdef __SSE4_2__, x86-only, leaving ARM on a scalar path.

C's real ceiling (cfast, ~48 M/s) came from two things Go can't easily do: inlining memchr so the whole parse schedules as one unit, and dropping validation. Go can't inline assembly — every SIMD call is a hard boundary — so it plateaus around 16 M/s single-core. But that plateau ships safely, portably, and allocation-free.

The 48 M/s trap

The fastest number is unusable. cfast assumes perfect input; on a truncated packet or missing \r\n it dereferences a null and takes the whole process down. For untrusted captured traffic, "returns an error" beats "3× faster and crashes."

In the pipeline

The win that actually mattered

Raw parse speed was a red herring. At the production rate of ~30k pairs/sec, the shipped Go pipeline uses ~2% of one core — the same workload that saturated every core with net/http. The lever was never nanoseconds; it was going from ~100 allocations per pair to zero, which drained the GC that was eating the CPU.

The full path — parse both buffers, shape the Kafka JSON, all in one allocation-free pass — replaced http.ReadRequest + header maps + json.Marshal and turned a CPU-bound service back into an idle one.
